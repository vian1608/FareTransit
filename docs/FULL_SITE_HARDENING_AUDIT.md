# FareTransit — Full-Site Hardening Audit

Date: 2026-08-08

This audit covers the production-facing React application, public landing pages, search flows, lead forms, customer account pages, booking lookup, passenger authorization, payments, car rentals, dynamic SEO routes, shared API behavior, and previously hardened admin workflows.

## Reliability contract

Every asynchronous customer/admin action should terminate in one of these states:

1. success with a visible result, or
2. failure with a visible message and a usable retry/navigation path.

A button must not remain indefinitely in a loading state. Canonical Axios calls have a global timeout, and legacy same-origin `/api/*` fetch calls now receive a bounded timeout when the caller has not supplied its own signal.

## High-priority findings fixed

### Payment-data safety

- Consulting Payment previously collected full card number and CVV before redirecting to hosted Stripe checkout. These fields were unnecessary and were removed completely.
- Consulting Payment no longer stores card/CVV values in sessionStorage.
- A shared transport guard removes raw PAN/CVV-like fields from Axios payloads, restricts card-last-four fields to four digits, and redacts card-like values from production console output.
- The shared guard also protects older customer flows while a dedicated tokenized payment integration is not present.

### Public lead forms

Flight route, train route, and Travel Assistance forms now:

- require genuine contact information;
- send the correct origin and destination instead of duplicating the full route title;
- send a client request/idempotency identifier;
- require `success === true`, `persisted === true`, and a real `leadId` before reporting success;
- fire the Google Ads Submit Lead Form conversion only after persistence;
- use visible normalized errors;
- reset loading state after failure.

The previous synthetic `route-inquiry@faretransit.com` fallback was removed.

### Dynamic SEO routes

- Arbitrary `/routes/*` slugs are no longer indexable by prefix.
- Only route slugs present in the actual route catalog receive indexable signals.
- Invalid route slugs render the real Not Found page rather than redirecting to the homepage.
- Invalid airline action slugs render Not Found instead of generating a fabricated airline name.
- Highly templated airline action pages remain noindex until they have enough airline-specific useful content to justify indexing.

### Car rentals

- View Deal no longer waits for analytics before redirecting to the provider.
- Invalid/non-HTTPS deal URLs show a visible error.
- Car-result pagination no longer feeds page-token changes back into the initial-search effect.
- Stale search responses cannot overwrite a newer result set.
- URL search parameters take precedence over stale sessionStorage.
- Popular airport links now provide usable future dates/times instead of relying on stale hard-coded fallback dates.
- Unsupported advisory-component props were removed.

### Flight search and return selection

- Legacy/new query naming is normalized (`return` → `returnDate`, `cabin` → `travelClass`) so shared/modified search URLs retain round-trip and cabin context.
- Return-flight API failures now display a real error and Retry Search action instead of looking like a genuine zero-result search.
- Loading state is released in `finally`.

### My Bookings

- `/my-bookings?code=...` links generated by authorization now auto-load the requested booking.
- The unreliable Retry Payment link that navigated to `/booking` without restoring itinerary context was removed.
- Customers can view the reservation or request payment/booking help without entering an invalid checkout state.
- Search failures are normalized and visible.

### Authentication

- Sign In and Sign Up now show visible errors for both thrown HTTP failures and API responses with `success: false`.
- Duplicate submits are blocked while the request is in flight.
- Loading states always reset.

### Indexed information pages

Contact, Terms, Privacy Policy, and Refund Policy now include page-specific title/description/canonical metadata using the canonical `https://www.faretransit.com` host.

## Existing protections verified

- Canonical host consolidation: `https://www.faretransit.com`
- Canonical public sitemap and robots file
- Private/admin/search/payment/booking routes protected by noindex
- Real Not Found route instead of catch-all homepage redirect
- Google Ads conversion helper uses persisted lead identity
- Shared Axios timeout and normalized admin errors
- Admin dashboard async/button reliability contract
- Admin destructive actions have explicit status results rather than indefinite loading

## Deliberately not live-tested against real customer data

A code/CI hardening pass must not create side effects just to prove a button works. The following should be exercised only with disposable/staging records and controlled recipients/providers:

- deleting real bookings;
- sending emails to real passengers;
- accepting a real passenger authorization;
- processing/refunding real payments;
- issuing or changing real tickets;
- modifying real traveler data.

For these operations, static route/handler contracts, request timeouts, error-state handling, build checks, and existing admin regression tests are used as the deployment gate.

## Remaining P1 engineering work

### Booking checkout payment UX

`BookingPage.js` still contains a legacy on-site card-number/CVV form. The new shared guard prevents raw payment credentials from being sent to the API and redacts them from production logs, but the strongest architecture is to replace that legacy collection UI with a real provider-hosted/tokenized element or with safe card-reference metadata only. This should be a dedicated payment-integration change rather than an unrelated SEO/UI refactor.

### Post-response email delivery

Booking creation still schedules some confirmation/admin email work after database creation using a post-response asynchronous path. In a serverless environment, a durable outbox/queue would be more reliable. This should be addressed with an explicit delivery architecture rather than by simply increasing request timeouts.

### SEO rendering architecture

The site is a React SPA. Technical crawl/indexing signals are now considerably cleaner, but route-level server rendering/static prerendering could improve deterministic HTML metadata/content delivery to crawlers and social preview tools. It is an architectural improvement, not a prerequisite for basic Google indexing.

## CI gate

`backend/tests/full_site_hardening_contract.test.mjs` protects the main changes above. It is included in both `npm test` and `npm run verify:production-ready` for the backend workspace.

The frontend production build remains a required CI gate.
